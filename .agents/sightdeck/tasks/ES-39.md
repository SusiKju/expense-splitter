# Klären, wo die Profilbilder der Standardpersonen gespeichert werden

Den Speicherort der Standard-Profilbilder finden (Repo-Ordner avatars/, Code, Firebase). Erklären, warum ein neues Event die Standardpersonen wieder mit dem aktuellen Bild anzeigt.

## Ergebnis

### Speicherort der Profilbilder

Es gibt zwei Arten von Avatar-Bildern:

1. **SVG-Karikaturen (im HTML eingebettet)**
   - Speicherort: `urlaubskasse.html`, Zeilen 1133–1141
   - Im JavaScript-Objekt `AVATARS` definiert
   - Für alle 7 Stamm-Personen: Ulbert, Thommy, Rudi, Ronny, Reddi, Micha, Long
   - Format: Inline SVG (viewBox 120x120)
   - Verhältnis zu Fotos: Karikaturen dienen als Fallback-Avatare

2. **Echte Fotos (JPG-Dateien im Repository)**
   - Speicherort: `/avatars/` Ordner im Repository Root
   - Dateien: `long.jpg`, `micha.jpg`, `ronny.jpg`, `rudi.jpg`, `thommy.jpg`, `ulbert.jpg`
   - Format: JPEG 192x192 Pixel
   - Größe: 8–15 KB pro Datei
   - Hinweis: "Reddi" hat kein Foto, nur Karikatur (SVG)
   - Verwaltung: Werden per Dateiname den Personen zugeordnet
   - Versionierung: Letzte Änderung 2026-09-24 (ES-38: Kontrast-Boost)

### Firebase/State

**Nicht in Firebase gespeichert!** 
- Avatare sind NICHT Teil des `state` (weder localStorage noch Realtime Database)
- Sie werden per Name (nicht per ID) referenziert
- Code-Kommentar (Zeile 1142): "Echte Fotos der Stamm-Truppe (avatars/*.jpg), per Name statt im State → gilt sofort in allen Kassen, eigenes Upload-Foto gewinnt"

### Warum ein neues Event die Standardpersonen mit aktuellen Bildern anzeigt

**Der Mechanismus:**

1. **Avatar-Lookup bei Person:**
   - Beim Laden des State (`loadState()`, Zeile 1170) oder bei neuen Events
   - Code Zeile 1186: `if (p.avatar === undefined) p.avatar = AVATARS[p.name] || null`
   - Der Avatar wird per **Personennamen** aus dem hardcodierten `AVATARS`-Objekt nachgeschlagen

2. **Warum aktuell:**
   - Das `AVATARS`-Objekt ist im HTML-Code eingebettet → es wird mit jedem Page-Load oder App-Update neu geladen
   - Die real Fotos werden über einen statischen HTTP-Path referenziert (z.B. `/avatars/long.jpg`)
   - Wenn die Dateien in `/avatars/` aktualisiert werden (wie in ES-38 geschehen), zeigt der Browser beim nächsten Zugriff automatisch die neuesten Versionen an

3. **Synchronisations-Verhalten (Firebase Events):**
   - Neue Events (z.B. neue Ausgabe) triggern einen State-Refresh
   - Der `loadState()`-Prozess lädt den persisted State, aber für jede Person ohne explizitem Avatar-Feld wird der Default nachgeschlagen
   - Die Person wird mit `AVATARS[personName]` verknüpft → aktueller Avatar
   - Eigene Fotos (hochgeladen & im State gespeichert) **überschreiben** diese Defaults

4. **Upload-Hierarchie:**
   - SVG/JPG-Default (per Name) → niedrigste Priorität
   - Eigenes hochgeladenes Foto → höchste Priorität
   - Code-Logik: `person.avatar` wird zuerst geprüft; wenn undefined, wird `AVATARS[name]` verwendet
