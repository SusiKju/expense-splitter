# Änderungsprotokoll: globale History statt Aufteilung pro Name, inkl. Wiederherstellung

Das Änderungsprotokoll ist aktuell pro Name aufgegliedert. Zu klären ist, warum das so gebaut wurde und ob eine gemeinsame History besser wäre. Diese History würde alle Änderungen zeigen: wer wann was hinzugefügt oder gelöscht hat. Zusätzlich wird ein Wiederherstellungsmechanismus für gelöschte Einträge vorgeschlagen. Ergebnis: Bewertung und Empfehlung, ob und wie das umgesetzt wird.

Offene Fragen: Soll die Wiederherstellung nur gelöschte Einträge betreffen oder auch bearbeitete? Wer darf wiederherstellen (alle oder nur der Ersteller der Kasse)?

## Resolution / Ergebnis

**Befund: Das Protokoll ist bereits eine globale History, nicht pro Name aufgeteilt.**
- `state.log` ist eine einzige chronologische Liste `{ts, action, deviceId, desc}` (`urlaubskasse.html:1211-1230`), synct mit dem Raum-State, max. 200 Einträge (`LOG_MAX`), neueste zuerst. Nur `saveExpense` (add/edit) und `deleteExpense` schreiben hinein (`:1547`, `:1573`).
- Der Name ist nur ein Präfix, der beim Rendern über `state.devices[deviceId] → Person` aufgelöst wird (bewusst rückwirkend, siehe ES-17). Nicht zugeordnete Geräte erscheinen als "Unbekanntes Gerät (abcd)". Vermutlich wirkt genau das wie eine Aufteilung pro Name: mehrere anonyme Geräte = mehrere "Namen", solange niemand "Dieses Gerät gehört" gesetzt hat.
- Warum so gebaut: Es gibt keinen Login, die Geräte-ID ist die einzige Identität; die Zuordnung zur Person liegt im Raum-State statt im Log, damit sie nachträglich korrigierbar ist.

**Empfehlung: keine Umstrukturierung, stattdessen kleine Nachschärfung + Wiederherstellung.**
1. Sichtbarkeit: Log steckt eingeklappt am Ende des Ausgaben-Tabs; ggf. eigener Tab/Button. Geräte-Zuordnung beim ersten Speichern einer Ausgabe erzwingen bzw. anbieten, damit keine "Unbekanntes Gerät"-Einträge entstehen.
2. Wiederherstellung ist machbar, aber nur mit Snapshot: Ein Delete-Eintrag hält heute nur `desc`, nicht die Ausgabe. Nötig: `before` (Kopie der Ausgabe, ~200 B) in Log-Einträgen für `delete` und `edit`. Restore = Ausgabe mit gleicher `id` zurück in `state.expenses` (bzw. `before` über die aktuelle Version legen) + neuer Log-Eintrag `restore`. Kein Rules-Change nötig (`state` ist frei validiert).
3. Stolperstein Beleg: `deleteExpense` löscht das Foto sofort aus `receipts/` (`:1574`). Ein Restore bekäme `hasReceipt` ohne Bild. Entweder Restore ohne Beleg (Hinweis anzeigen) oder Beleg-Löschung erst beim Herausfallen aus dem Log.
4. Stolperstein Sync: Der ganze State wird per `set()` überschrieben (last write wins, `:2004`); zwei gleichzeitige Änderungen können sich gegenseitig samt Log-Eintrag verlieren. Vorbestehendes Risiko, durch Restore nicht schlimmer.
5. Aufbewahrung: Mit Snapshots wird 200 Einträge (edit = 2 Objekte) noch klein; das Limit kann bleiben.

**Offene Fragen, mit Empfehlung:**
- Nur gelöschte oder auch bearbeitete? → Beides über denselben `before`-Snapshot; erst nur Löschen (Hauptfall), Edit-Undo optional.
- Wer darf wiederherstellen? → Alle Mitglieder. Ersteller-only ist ohne Auth nicht durchsetzbar (`rooms/$code` ist `.write: true`, Ersteller-Prüfung wäre reines UI-Theater). Geschlossene Kasse: gesperrt (`guardClosed`), wie alle Änderungen.
- Auch Personen/Einstellungen/Schließen loggen? → Nicht nötig für Restore; wäre eigenes Ticket.

**Aufwand:** Nachschärfung Sichtbarkeit ~S, Restore für Löschen ~M (Snapshot, Button, Log-Aktion `restore`, Test). Kein Umsetzen ohne Freigabe.
