# Identitätsbetrug beim Raumbeitritt verhindern (personenbezogener Code)

Wer den Raumcode hat, muss sich beim Betreten einer eingetragenen Person zuordnen. Heute kann er dabei aber auch einen fremden Namen anklicken und sich als diese Person ausgeben. Gesucht sind Ideen, wie man das verhindert und die Zuordnung pro Person absichert. Ein Vorschlag aus der Eingabe ist ein eigener Code für jede Person. Ergebnis ist eine Empfehlung mit Vor- und Nachteilen, noch kein fertiger Code.

Offene Fragen: Soll das auch für bestehende Räume und schon zugeordnete Geräte gelten? Wie viel zusätzlicher Aufwand beim Beitreten ist für die Nutzer in Ordnung?

## Resolution / Ergebnis

**Rahmenbedingung zuerst:** `database.rules.json` hat `.read: true` / `.write: true`
auf dem ganzen Raum, es gibt keine Firebase-Auth. Jeder mit dem Raumcode kann die
komplette DB lesen und schreiben — jedes serverseitig geprüfte Geheimnis (PIN,
Hash, Token) liegt also selbst im Klartext für jeden Code-Inhaber offen, sobald es
im State steht. Echte, angriffsfeste Absicherung geht nur mit richtigem Auth
(Login pro Person, Rules die `auth.uid` prüfen) — für einen Urlaubskassen-Tool
unter Freunden unverhältnismäßig (Account-Zwang, Migration, neue Fehlerklassen).

**Das eigentliche Problem ist kein Angreifer, sondern die UI:** Aktuell zeigt
`ensureIdentity()` jedem, der den Raumcode hat, eine anklickbare Liste **aller**
Namen — das lädt zu versehentlicher oder spontaner Falschzuordnung ein ("ich klick
einfach auf wen anders"). Das lässt sich beheben, ohne echte Kryptografie
vorzutäuschen, die die offene DB sowieso nicht halten würde.

**Bewertete Optionen:**

1. **Persönlicher PIN pro Person** (Vorschlag aus der Eingabe) — PIN beim
   Anlegen vergeben, bei Auswahl abfragen. *Contra:* PIN liegt wegen der offenen
   Rules trotzdem für jeden lesbar in der DB (Hashing hilft bei 4-stelligen PINs
   kaum), macht **jeden** Beitritt einen Schritt umständlicher, löst das eigentliche
   Problem (öffentlich anklickbare Namensliste) nicht — sie bliebe stehen.
2. **Personenbezogener Einladungslink statt geteilter Raumcode** (empfohlen) —
   pro Person wird beim Anlegen ein Token erzeugt (`?room=CODE&p=TOKEN`), analog zum
   bestehenden `inviteUrl()`/QR-Mechanismus. Der Link geht direkt an die Person
   (WhatsApp etc.) statt an die Gruppe. Beim Öffnen mit gültigem `p=` wird die
   Identität automatisch gesetzt, `ensureIdentity()` mit der Namensliste entfällt
   für diesen Weg komplett. **Ohne** `p=` (alter Raumcode, QR ohne Personenbezug)
   bleibt der heutige Namens-Modal als Fallback bestehen — nichts bricht.
   *Vorteil:* behebt genau das UX-Problem (keine fremde Namensliste mehr im
   Normalfall sichtbar), nutzt bestehende Mechanik, macht den Beitritt für den
   Normalfall sogar **einfacher** (kein Auswählen nötig). *Contra:* Ersteller
   verschickt N Links statt einem Code/QR; ein weitergeleiteter Link umgeht den
   Schutz genauso wie heute ein weitergeleiteter Code — bleibt bewusst offen, das
   ist kein Angriffsschutz, sondern verhindert die versehentliche Fehlzuordnung.
3. **Echtes Auth** (Firebase Anonymous/Email-Auth + Rules auf `auth.uid`) —
   einzige Option mit echter Absicherung, aber Aufwand und Nutzerreibung stehen in
   keinem Verhältnis zum Tool. Verworfen.

**Empfehlung:** Option 2 (personenbezogener Einladungslink), mit dem heutigen
Namens-Modal als Fallback für den klassischen Raumcode-Weg.

**Offene Fragen beantwortet:**
- *Bestehende Räume/Geräte:* keine Migration nötig. Bereits gesetzte
  `state.devices[deviceId]`-Zuordnungen bleiben unangetastet; Tokens werden nur
  für künftig neu angelegte Personen vergeben, alte Räume funktionieren über den
  Fallback (Namensliste) unverändert weiter.
- *Zusätzlicher Aufwand beim Beitreten:* keiner — im Normalfall (Link mit `p=`)
  entfällt ein Klick gegenüber heute, weil die Auswahl automatisch passiert. Der
  Mehraufwand liegt einmalig beim Ersteller (pro Person einen Link statt einem
  Code teilen).

Kein Code in diesem Task — Umsetzung (Token-Erzeugung, Link-UI pro Person,
`p=`-Parsing beim Join) ist ein Folge-Task.
